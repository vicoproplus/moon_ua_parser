## 1. 剖析方法

- 语料照常全量加载（10,000 条，`sample_set_hash` 与 T-04 基线一致：
  `sha256:3640d3b7…`）；计时单元为 stride-50 分层子样本 200 条。
- 1 轮不计时预热 + 3 轮计时重复；每轮分别整段计时
  `parse_browser` / `parse_os` / `parse_device` / 完整 `parse`
  （4 个 pub API，未动发布面）。表中占比 = 各域**中位** ns/call ÷ 完整
  parse 中位 ns/call。
- **模板替换耗时 = full − (browser+os+device)，上界口径**：三条单域 pass
  各自多付一次循环开销，且跨段噪声可把差值推成负数——按实测报告，不修匀。
- 规则试验次数：不计时地跑一遍 `parse(ua, with_rule_index=true)`，读每域
  `rule_index`：命中于索引 i ⇒ 该域做了 i+1 次正则试验；miss ⇒ 扫满该域全部
  规则（ua 433 / os 204 / device 633，共 1270，见生成文件
  `src/ua_parser/rules/rules_data.mbt`）。
- 所有 pass 折入 checksum 并跨轮/跨后端比对（`profile-rep` /
  `profile-checksum` 行）：4 次运行 `samples_checksum=6122` 完全一致，
  `domain_sums_match=true`、`index_matches_full=true`、`reps_consistent=true`
  —— 排除死代码消除与跨轮漂移。

## 2. 实测数据（native --release，run 1，3 次重复的中位）

| 域 | ns/call（中位） | 占完整 parse 比 |
|---|---|---|
| browser（`parse_browser`） | 15,682,309.50 | **41.47%** |
| os（`parse_os`） | 1,469,803.00 | **3.88%** |
| device（`parse_device`） | 20,657,575.99 | **54.63%** |
| 模板替换（上界 = full − 三域和） | 178.00 | **0.00%**（0.0005%） |
| 完整 parse | 37,809,866.50 | 100% |

- 三域份额和 = 99.98%，与 full−(b+o+d)=178 ns 自洽。
- 重复轮散布：full 三轮 37.80–38.23 ms/call，(max−min)/中位 = **1.14%**。
- js 后端（run 3）同型：browser 41.22% / os 3.75% / device 54.03% /
  模板上界 0.97%（133,987 ns）；full 13,682,410.50 ns/call。与 native 逐域
  份额差 ≤ 0.97 个百分点 —— 占比结论跨后端稳定。

## 3. 规则试验统计（决定性证据，run 1；js run 3 完全相同）

| 域 | 规则数 | 命中率 | 命中索引 avg / median / max | 每次parse平均试验数 |
|---|---|---|---|---|
| browser | 433 | 200/200 | 197.18 / 186 / 398 | 198.2（45.8% 深度） |
| os | 204 | 200/200 | 31.56 / 19 / 195 | 32.6（16.0% 深度） |
| device | 633 | 191/200（miss 9 ⇒ 扫满 633） | 448.53 / 457 / 632 | 457.8（72.3% 深度） |

- 每 parse 平均正则试验总数 = (39,636 + 6,512 + 91,557) / 200 ≈ **688.5 次**。
- 单次试验成本（ns/call ÷ 试验数/call）：browser **79.1 µs**、os **45.1 µs**、
  device **45.1 µs**；加权 37.81 ms ÷ 688.5 ≈ **54.9 µs/次**。
  browser 单价最高 —— 其模式含大量交替/嵌套分组，Pike-VM 线程集更宽。

## 4. Top 热点函数记录

本工具链无采样型函数剖析器；以下排序为**测量归因**（按域拆分 + 模板上界 +
确定性试验次数 + 源码结构），非采样剖面，特此声明：

1. **`@regexp.Regexp::execute` → `vm` / `add_thread`**（依赖
   moonbitlang/regexp@0.3.5，`.mooncakes/.../internal/vm/impl.mbt`）——
   **≥99%**：三域扫描合计 99.98% 的耗时，其内容就是 ~688.5 次/parse 的
   `execute` 调用（每次 = 对整条 UA 的非锚定 Pike-VM 仿真，per-execute 还要
   分配 `inst_gen`/`clist`/`nlist` 与线程结构）；扫描循环本身只有 ~1270 次
   下标递增，量级在 ns 级，与 54.9 µs/试验相比不可测。
2. **模板/捕获组求值**（`src/ua_parser/template.mbt`：`eval_template` /
   `eval_field` / `eval_ua_family` / `eval_ua_version` / `get_group`）——
   **≤1%（上界）**：三次运行的上界读数 0.00% / 0.92% / 0.97%，且仅在命中的
   3 条规则上各求值一次。
3. **扫描循环管线**（`engine.mbt:first_match`、`matcher.mbt:match_os` /
   `match_device`）：无独立测量手段，被 1) 吸收；上界 ~1270 次数组下标操作。

## 6. 结论（按计划 Step 2/3 二选一 + Step 3 停止条款）

**结论：热路径瓶颈明确，但任何实质加速都属于引擎级重构 → 按计划 Step 3
停止实现，产出回 P5 补 PRD 的具体建议（见 §8）。**

依据（三段论，全部有 §2–§5 数据支撑）：

1. **99.98% 的耗时在正则试验**（~688.5 次/parse × 54.9 µs/次），模板替换
   ≤1% 上界，循环管线不可测 —— 本库（src/ua_parser）内部没有任何一个
   "单变量"杠杆能碰到主要成本；
2. **小优化路线已穷尽并实测否决**：唯一在册候选（`execute` → `match_`，
   免除非命中试验的 `MatchResult`/before/after 构造，3 处调用点、单一机制）
   实测 full 中位 38,344,615.50 vs 37,809,866.50 ns/call（**+1.4%，落在
   1.14% 轮内散布与 ±10–17% 跨运行方差之内，无可测改善**）→ 已还原，
   `git diff moon_ua_parser_lib/src` 对 HEAD 为空（字节级一致）；
   【标注】该候选属**症状修复**级（省一次分配，不减试验次数），按数据否决；
3. **「无需优化」论证不成立**：T-04 基线 42.30 ms/parse（native 中位）距
   smoke 占位门限 100 ms 仅 2.4× 余量，且瓶颈是结构性的（1270 条非锚定规则
   顺序试验）——若宣称"无需优化"，必须论证热点占比无害，而实测恰恰相反；
   【标注】真正的**根因修复**（降低试验次数/单价）= §8 的引擎级方案，按
   裁决（b）（"规则索引/预筛选器、Aho-Corasick 类改造"）禁止在本单元实装。

## 8. 回 P5 补 PRD 的具体建议（引擎级，不进本单元）

**建议标题**：引擎级匹配加速 —— 规则预筛选/索引（literal prescreen / rule
bucketing）。**级别**：P5（性能优化类）。**性质标注**：根因修复类。

- **问题陈述（实测）**：99.98% parse 耗时 = ~688.5 次顺序正则试验/parse
  （native ~54.9 µs/次）；device 域独占 54.6%（平均扫 633 条中的 72.3% 深度，
  4.5% 样本全扫）。
- **候选方案（供 PRD 评审取舍）**：
  - A. **字面量预筛**：`scripts/gen_rules.py` 生成期从每条模式提取"必需
    字面量"（最长确定字面交替支/首个定串）；匹配期先做子串存在性检查，缺失
    则跳过 `execute`。构造上保语义（必需字面量不在 ⇒ 正则必不命中）；对含
    空支交替等无必需字面量的模式保守回退全试。判别门：differential 18213
    三域 100% + 输出逐字节不变。
  - B. **规则分桶/索引**：按 token 键（"Windows"/"Android"/"iPhone"…）把
    规则组织为候选桶，无键规则落全扫桶。
  - C. **锚定快路径**：带 `^` 前缀的模式按位置检查（uap-core 多数模式非
    锚定，预期收益小）。
  - D. **VM 层降耗**：moonbitlang/regexp 每次 execute 重复分配
    `inst_gen`/`clist`/`nlist` 与线程结构（internal/vm/impl.mbt）——属上游
    依赖改造，需自建 fork/上游贡献评估。
  - 预期量级：A/B 合计可将试验数降 3–10×（无字面量兜底规则为长杆），现实
    目标 native ~5–15 ms/parse。
- **验收草案**：`moon info` 对 src/ua_parser 零 diff；differential 18213
  三域 100% 不变；T-04 协议 3+3 默认基准对比且提升 ≥ 立项时约定阈值；
  `--profile` 份额复测入档；evidence 落盘。
- **风险**：JS 方言模式字面量提取的正确性（保守提取只增不漏）；生成器复杂
  度；与 uap-core 快照更新（73e7340 → 未来）的再生成耦合。
